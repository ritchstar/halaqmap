**الهدف من هذا الملف:** إعطاؤك (كروسور) كل السياق والنتائج والتحذيرات الحرجة اللازمة لمتابعة هذا المشروع بدون أي تخمين أو إعادة اكتشاف لما تم فعلاً.

## 1) خطوات تطبيق الـ bundle (نفس أسلوب التسليم السابق الذي نجح معك)

القاعدة (base) التي بُني عليها البندل هي نفسها المستخدمة في التسليم السابق:
```
56858c9 Update solution catalog hero headline to emphasize custom workflows.
```

الـ commits الأربعة داخل البندل، من الأقدم للأحدث:
```
5524351 Replace solution catalog rows with full-image product cards
8f31fa8 Add tabkhatuna1 and halana1 to the solution catalog
8e04f2f Generate real catalog marks and cards for tabkhatuna1 and halana1
8ea4ac2 Update product theme colors for halana, kitchen, produce, grocers   <- الجديد في هذا التسليم
```

**إذا كنت طبّقت التسليم السابق (`halaqmap-catalog-updates.bundle`) بالفعل ودفعته لـ origin/main**، فإن أول 3 commits ستكون موجودة عندك مسبقًا، ولن يحتاج git لتطبيقها مرة أخرى (fast-forward تلقائي) — فقط الـ commit الرابع (`8ea4ac2`، الألوان) هو الجديد فعليًا. الخطوات التالية تعمل بأمان في الحالتين:

```bash
cd /path/to/local/halaqmap   # مجلد المشروع لديك
git fetch /path/to/halaqmap-theme-and-catalog-updates.bundle HEAD:incoming-theme-updates
git log --oneline incoming-theme-updates -4
```

يجب أن تشاهد بالضبط الأربعة أعلاه. ثم:

```bash
git checkout main
git pull        # تأكد أنك محدّث مع origin/main أولاً
git merge incoming-theme-updates
```

إذا ظهر أي تعارض على `src/config/storeSolutionCatalog.ts` أو `scripts/build-store-solution-catalog-marks.mjs` (لأنك ربما دمجت جزءًا منها يدويًا سابقًا)، راجع التسليم السابق (`cursor_instructions.md` في نفس المجلد) — نفس الحل المذكور هناك (`git cherry-pick 8f31fa8 8e04f2f` بدل الدمج الكامل) ينطبق هنا أيضًا، مع إضافة:

```bash
git cherry-pick 8ea4ac2   # تعديل الألوان — لا يتعارض عادة لأنه ملف تكوين واحد فقط
```

تحقق نهائي قبل الدفع:
```bash
git diff main origin/main -- src/config/storeProductThemes.ts
npx tsc --noEmit
git push origin main
git branch -D incoming-theme-updates   # اختياري
```

**ملخص ما يضيفه commit `8ea4ac2` تحديدًا (الجديد في هذا التسليم):** تعديل ألوان `STORE_PRODUCT_THEMES` في `src/config/storeProductThemes.ts` فقط — أربعة كائنات ألوان (halana/kitchen/produce/grocers) لتطابق الهوية البصرية التي صممتها Chatly لكل منتج (راجع `theme_preview.html` للمعاينة قبل/بعد). **لم يُغيَّر أي منطق، أي route، أي مكوّن React — فقط قيم hex في ملف تكوين واحد.** تم التحقق بـ `npx tsc --noEmit --ignoreDeprecations 6.0 -p .` وعاد بصفر أخطاء.

## 2) السياق الكامل: ما هو هذا المشروع ولماذا

طلب المستخدم نقل "روح" التصميم الحديث الذي أنتجته أداة Chatly (منشئ تطبيقات بالذكاء الاصطناعي، chatlyai.app) لأربعة منتجات "جار الحي" — **حلانا1، خضارنا1، تمويناتا1، طبختنا1** — إلى الكود **الحقيقي** لموقع halaqmap.com، بدون كسر أي منطق عمل حقيقي (مدفوعات ميسر، مزامنة حية، مواقع GPS، إلخ).

بما أن مزامنة GitHub داخل Chatly معطوبة (خطأ خلفي "repo_name is required")، وبما أن إعطاء كروسور تعليمات مجردة سابقًا لم ينتج عنه تغيير حقيقي، تم استخراج **كود Chatly الحرفي** يدويًا من داخل واجهة الدردشة (نسخ/لصق من كتل الكود الفعلية في الدردشة)، والتحقق من سلامة كل ملف عبر مترجم TypeScript (0 أخطاء لكل الملفات)، ثم فحص **الكود الحقيقي** في الإنتاج بعمق لمعرفة أين وكيف يمكن تطبيق هذا التصميم بأمان.

**نتيجة الفحص الأهم:** تصميم Chatly افترض متجرًا كلاسيكيًا (شبكة منتجات + سلة + دفع فوري لكل عنصر) لكل الأربعة. **هذا لا يطابق نموذج العمل الحقيقي إطلاقًا.** راجع القسم 3.

---

## 3) ⚠️ سياسة العمل الحقيقية — يجب ألا تُخالَف أبدًا مهما كان تصميم Chatly

**تعليمات صريحة من صاحب المشروع:** *"يجب أن تطابق جميع المنتجات سياستنا بغض النظر عن تصميم شاتلي."*

النموذج الحقيقي (مؤكَّد بالكود وبنصوص الواجهة نفسها، في المنتجات الأربعة بلا استثناء):

- صاحب النشاط (الجارة/الجار) يدفع **اشتراكًا واحدًا** لهالاقماب عبر **ميسر حقيقي** (Moyasar، بطاقة/Apple Pay) لتفعيل صفحته العامة + لوحة تشغيله. الأسعار تختلف بالمنتج (300–2500 ريال حسب الباقة والمدة).
- بعدها، **الزبون النهائي لا يدفع لهالاقماب أبدًا وبأي شكل**. الدفع بين الزبون وصاحب النشاط مباشرة: نقدًا، أو شبكة عند التسليم/الاستلام، أو تحويل بنكي/STC/سارية يدوي مع رفع صورة إثبات دفع. **لا عمولة، لا تحصيل عبر البوابة على قيمة الطلب** — هذا مذكور صراحة في نصوص كل منتج (مثال: "لا تحصيل سلة عبر ميسر"، "لا عمولة على قيمة السلة").
- أي إعادة تصميم بصري **يجب ألا توحي بعكس ذلك** — أي زر أو Dialog "ادفع الآن" لقيمة الطلب نفسه (وليس الاشتراك) يخالف السياسة ويجب ألا يُضاف، حتى لو كان تصميم Chatly يتضمنه.

**الخلاصة العملية لكروسور:** أي عمل بصري لاحق (ألوان/أشكال/تخطيط) مسموح ومرحّب به. أي عمل يمس مسار الدفع، أو يضيف ميزة عمل جديدة (مثل ربط حقيقي بالبوابة لكل طلب، أو ميزة إحالة/حملة حقيقية)، **يحتاج قرارًا صريحًا من صاحب المشروع أولاً — لا تفترضه من تصميم Chatly.**

## 4) خريطة المطابقة الصحيحة بين تصميم Chatly والمنتجات الحقيقية

⚠️ **تصحيح مهم:** التسمية في Chatly لا تطابق التسمية في الكود الحقيقي حرفيًا. الخريطة الصحيحة المؤكَّدة:

| اسم Chatly | اسم الإنتاج الحقيقي (كود) | الفئة | جذر الراوت |
|---|---|---|---|
| حلانا1 | `halana` | حلويات منزلية | `/h/:token`, `/store/halana`, `/pay/halana/:token` |
| خضارنا1 | `produce` (وليس grocers!) | خضار وفواكه | `/v/:token`, `/store/produce`, `/pay/produce/:token` |
| تمويناتا1 | `grocers` (وليس produce!) | تموينات/بقالة | `/g/:token`, `/store/grocers`, `/pay/grocers/:token` |
| طبختنا1 | `kitchen` | طبخ منزلي | `/k/:token`, `/store/kitchen`, `/pay/kitchen/:token` |

جميع الأربعة تشترك في نفس البنية المعمارية:
- صفحة هبوط تسويقية عامة (تبيع الاشتراك لصاحب النشاط).
- **صفحة واحدة فقط** (`Store*ShopPage`) تتفرّع لعرضين مختلفين تمامًا حسب نهاية الرابط: `/desk` = لوحة تشغيل صاحب النشاط، وإلا = واجهة الزبون. هذا ليس صفحتين منفصلتين في الراوتر — تذكّر هذا عند أي إعادة هيكلة.
- صفحة دفع Moyasar منفصلة (`/pay/<product>/:token`) للاشتراك فقط.
- كل الألوان والأشكال المشتركة تُقرأ من ملف واحد: **`src/config/storeProductThemes.ts`** (تم تعديله بالفعل، انظر القسم 1) + `src/styles/storeProductTheme.css` (فئات CSS مشتركة بين الأربعة تحت بادئة `halana-*` رغم أنها تُستخدم للأربعة كلهم — هذا اسم تاريخي وليس خطأ).

**المكتبة البصرية مختلفة:** الإنتاج يستخدم **Radix UI** (`@radix-ui/react-*`) عبر shadcn (`src/components/ui/*`). تصميم Chatly مبني على **`@base-ui/react`** (مكتبة مختلفة تمامًا، API مختلف مثل `render` prop بدل `asChild`). **لا يمكن نسخ مكوّنات `ui/*` من `chatly_export_reference.zip` مباشرة — يجب إعادة كتابة أي JSX جديد ليستخدم مكوّنات `src/components/ui/*` الموجودة فعليًا في الإنتاج.**

## 5) ملخص الفحص لكل منتج — أين يتطابق تصميم Chatly مع الواقع وأين لا يتطابق

### حلانا1 (`halana`) — أكبر فجوة
- **الواقع:** ليس متجرًا بسلة إطلاقًا. الزبون يستعرض معرض أعمال (`HalanaActivityShowcase`)، يطلب "طلب مخصص" عبر معالج من 4 خطوات (`HalanaActivityOrderFlow`, يحتوي حقل خداع honeypot ضد الروبوتات لا يجوز حذفه)، صاحبة النشاط تُسعّر يدويًا، ثم دفع تحويل بنكي يدوي.
- **الملفات الحقيقية الأهم:** `src/pages/store/StoreHalanaShopPage.tsx`, `src/components/store/halana/HalanaDeskStudio.tsx` (742 سطر، لوحة التشغيل الفعلية — أكبر وأخطر ملف)، `src/components/store/halana/HalanaActivityShowcase.tsx`, `HalanaActivityOrderFlow.tsx`, `src/pages/store/StoreHalanaPayPage.tsx` (Moyasar الحقيقي، عالي الخطورة).
- **لا يوجد GPS إطلاقًا في حلانا1.**
- تصميم Chatly (شبكة منتجات + سلة + Dialog دفع) **لا يمكن تطبيقه حرفيًا** — إعادة التصميم هنا يجب أن تقتصر على الألوان/الطباعة/شكل البطاقات المطبَّقة على المكوّنات الحقيقية أعلاه، وليس استبدال بنيتها.

### خضارنا1 (`produce`)
- **الواقع:** يشبه تصميم Chatly أكثر من غيره — يوجد فعلاً سلة صغيرة حقيقية (`StoreProduceShop.tsx`، منتجات + كميات + إجمالي)، لكن "الدفع" تجميلي فقط (نقدي/شبكة عند التسليم، أو تحويل يدوي) وليس ميسر حقيقي لكل طلب. السعر المعروض **تقدير فقط** حتى تؤكد صاحبة النشاط التوفر — لا تجعل تصميمك الجديد يوحي بسعر نهائي مقفل.
- **يوجد GPS حقيقي وفعلي:** خدمة "تعال" (`src/lib/storeProduceCome.ts`) — تتبع قرب بالإحداثيات (عتبة 250 متر haversine) + إشعار متصفح عند اقتراب البائع المتجول. هذا يطابق فكرة "يجيك" التي صممتها Chatly لخضارنا1 — نقطة تقاطع جيدة، حافظ على هذا المنطق تمامًا عند أي إعادة تصميم.
- **الملفات الأهم:** `StoreProduceShopPage.tsx`, `StoreProduceShop.tsx` (451 سطر، أكبر ملف)، `StoreProduceDesk.tsx`, `storeProduceCome.ts`.

### تمويناتا1 (`grocers`)
- **الواقع:** نفس نموذج خضارنا1 (سلة تجميلية + دفع يدوي)، لكن GPS هنا أضعف بكثير — فقط زر "استخدم موقعي" لتعبئة نص العنوان مرة واحدة، وليس تتبع قرب حقيقي.
- ⚠️ **ميزة `maskPii` (إخفاء اسم/هاتف/عنوان الزبون) التي صممتها Chatly موجودة فعلاً بالكود** في `StoreGrocersDesk.tsx`، **لكن فقط للعرض التجريبي الوهمي في صفحة التسويق** (`StoreGrocersStudio.tsx` تمرر `maskPii={isLab}`) — **لا يوجد أي زر حقيقي** يتيح لصاحب المتجر إخفاء بيانات زبائنه الحقيقية أثناء عرض لوحته لشخص حقيقي. تطبيق فكرة Chatly كميزة حقيقية = **عمل برمجي جديد**، وليس مجرد إعادة تلبيس. **لا تنفّذه إلا بطلب صريح من صاحب المشروع.**
- **الملفات الأهم:** `StoreGrocersShopPage.tsx`, `StoreGrocersShop.tsx` (451 سطر)، `StoreGrocersDesk.tsx`, `StoreGrocersPayPage.tsx`.

### طبختنا1 (`kitchen`) — أهم تحذير في كل هذا التسليم
- **الواقع العام:** نفس نموذج السلة التجميلية + الدفع اليدوي. يوجد GPS حقيقي فعلي (تحديد نقطة استلام صاحب المطبخ + تعبئة عنوان توصيل الزبون)، مطابق تقريبًا لما صممته Chatly.
- ⚠️⚠️ **"مركز النمو" الذي صممته Chatly (نص حملة + عدادات مشاركات/عملاء جدد/هدايا + زر نشر) لا يطابق صفحة "Growth Hub" الحقيقية في الكود إطلاقًا.** صفحة Growth Hub الحقيقية (`/k/:token/desk/growth`, `StoreKitchenGrowthHubPage.tsx`) هي **مجرد مكتبة نصوص تسويقية جاهزة للنسخ** (رسائل واتساب/سناب جاهزة) بدون أي حالة أو أرقام أو نموذج حملة — ملف `storeKitchenGrowthHub.ts` يقول حرفيًا في تعليقه: **"بلا أسعار اشتراك وبلا تجربة وبلا إرسال جماعي"**.
- **الميزة التي تطابق فعليًا** فكرة Chatly (حملة + عدادات + جوائز) هي نظام **منفصل تمامًا** اسمه "هدية طبختنا1" (`/store/kitchen/gift*`, `storeKitchenGiftCampaignRemote.ts`, `storeKitchenGiftCampaign.ts`): قرعة فنية حقيقية على 5 اشتراكات مجانية، بحد 50 مشتركًا مؤهلاً لكل دورة، **تأكيد بريد إلكتروني مزدوج إلزامي** قبل احتساب أي تسجيل، حقل خداع (honeypot) ضد الروبوتات، ونافذة 72 ساعة لإعادة توزيع الجائزة إن لم يُطالَب بها الفائز.
- **إذا طُلب منك تطبيق تصميم "مركز النمو" لـ Chatly حرفيًا:** لا تربطه بمسار `/desk/growth` الحقيقي (سيُظهر أزرارًا لميزات غير موجودة فعليًا: "نشر حملة"، "نسخ رابط إحالة" — لا يوجد رابط إحالة ولا نشر حملة في الكود الحقيقي). إن كان الهدف تصميمًا بصريًا فقط لصفحة "Growth Hub" الحقيقية (مكتبة النصوص)، طبّق الألوان/الأشكال فقط بدون عناصر الحملة. إن كان الهدف ميزة إحالة حقيقية بمقاييس فعلية، فهذا **قرار عمل منفصل** يُبنى فوق نظام "الهدية" الموجود (أو نظام جديد كليًا) — **اسأل صاحب المشروع صراحة قبل أي افتراض.**
- **الملفات الأهم:** `StoreKitchenShopPage.tsx`, `StoreKitchenShop.tsx` (377 سطر)، `StoreKitchenDesk.tsx` (385 سطر)، `StoreKitchenGrowthHubPage.tsx` (الحقيقية، بسيطة)، `storeKitchenGiftCampaignRemote.ts` + `storeKitchenGiftCampaign.ts` (نظام الهدية الحقيقي بمنطق مضاد للاحتيال).

## 7) ما لم يُنفَّذ بعد — قرارات مفتوحة تحتاج توجيهًا صريحًا من صاحب المشروع (وليس افتراضًا من كروسور أو Chatly)

1. تحسين شكلي إضافي (زوايا البطاقات/الظلال/التباعد) في `src/styles/storeProductTheme.css` لتقريب "الإحساس" العام أكثر من لمسة Chatly — منخفض الخطورة، لم يُطلَب بعد بشكل نهائي.
2. أي تغيير على مستوى JSX/بنية الصفحات الأربعة (أبعد من الألوان) — **يتطلب مراجعة ملف بملف** بسبب حجم منطق العمل الموثّق في القسم 5، وليس عملية دمج آلية.
3. ميزة `maskPii` الحقيقية لتمويناتا1 (قرار عمل جديد، ليس إعادة تلبيس).
4. أي ربط بين تصميم "مركز النمو" ونظام "الهدية" الحقيقي في طبختنا1 (قرار عمل جديد).
5. استخراج `src/app/layout.tsx` من Chatly (لم يُستخرَج بعد) وصور المنتجات الوهمية (webp) التي ولّدتها Chatly — غير حرجة، يُحتمل عدم الحاجة إليها إن استُخدمت صور الإنتاج الحقيقية بدلاً منها.

## 8) ملخص تنفيذي من سطرين لكروسور

طبّق البندل وادفعه (قسم 1) — هذا وحده تغيير آمن 100%. بعدها **لا تبدأ أي عمل بصري إضافي أو منطقي بناءً على تصميم Chatly بمفردك** — القسمان 3 و5 يحتويان تحذيرات حرجة (خصوصًا مركز النمو/الهدية في طبختنا1) يجب مراعاتها، وأي خطوة أبعد من الألوان تحتاج توجيهًا صريحًا جديدًا من صاحب المشروع.
