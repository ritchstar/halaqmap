# تكليف كروسور — إعادة تصميم لوحة تشغيل خضارنا1 على طراز Chatly (مسار أ)

**إلى:** كروسور
**الحالة:** بعد التحقق الكامل من كود مسار (ب) (تلميع الواجهة الأمامية) — راجعته بنفسي (سحب، tsc، مراجعة ديف) وكله سليم. هذا هو تكليف مسار (أ): **لوحة تشغيل خضارنا1** (`/v/produce-lab/desk` وما يعادلها).
**النطاق:** `produce-lab` فقط — تماماً بنفس منطق البوابة المستخدم في مسار (ب). لا تُغيَّر لوحة أي منتج آخر (تمويناتا1/طبختنا1/حلانا1)، ولا لوحة خضارنا1 لأي توكن حقيقي آخر غير `produce-lab`.

---

## 1) الوضع الحالي — مهم قبل البدء

فحصتُ الكود فعلياً ووجدت أن اللوحة (`StoreProduceDesk.tsx`) لديها بالفعل **تلوين CSS فقط** مطبّق مسبقاً (كلاس `produce-chatly-desk` في `src/styles/produceChatly.css`، مُفعّل من `StoreProduceShopPage.tsx` عندما `desk && chatlyUi`). هذا التلوين يُبقي نفس الهيكل القديم (صفحة واحدة طويلة تُمرَّر للأسفل) لكن بألوان كريمية/خضراء بدل الداكن.

**هذا التكليف (أ) يطلب أبعد من التلوين:** إعادة هيكلة كاملة على طراز الملف المرجعي التالي (Chatly الأصلي لخضارنا1 — عندي نسخة كاملة منه محفوظة، وسأرفقها/أصفها بنداً بنداً أدناه): قائمة جانبية (Sidebar) + أقسام تبويب (نظرة عامة / الطلبات / المنتجات والمخزون / الموقع والساعات / الدفع المباشر / أدوات المشاركة)، بدل الصفحة الواحدة الطويلة.

---

## 2) القاعدة الذهبية — لا منطق مزيف، فقط واجهة جديدة فوق نفس المنطق الحقيقي

مرجع Chatly (`khudarana-operations.tsx`) مبني بالكامل على **بيانات وهمية ثابتة** (`useState` محلي، طلبات وهمية، دردشة وهمية بردود جاهزة، "7 متصفحين الآن" رقم ثابت). **ممنوع نقل أي من هذه البيانات الوهمية إلى الإنتاج.** كل عنصر في التصميم الجديد يجب أن يُغذّى من نفس الخطافات (hooks) والمكوّنات الحقيقية المستخدمة في `StoreProduceDesk.tsx` الحالي — لا يُعاد اختراعها، فقط تُعاد صياغتها بصرياً داخل الهيكل الجديد.

الطريقة المعمارية المطلوبة (نفس نمط النجاح في مسار ب تماماً):

- **إنشاء مكوّن جديد** `src/components/store/produce/ProduceChatlyDesk.tsx` بنفس توقيع props الموجود في `StoreProduceDesk` تماماً:
  ```ts
  {
    state: ProduceLabState;
    onChange: (next: ProduceLabState) => void;
    shopUrl: string;
    token: string;
    showTrialNote?: boolean;
  }
  ```
- **البوابة** في `src/pages/store/StoreProduceShopPage.tsx` (السطر ~213-220 حالياً):
  ```tsx
  desk ? (
    chatlyUi ? (
      <ProduceChatlyDesk state={state} onChange={commit} shopUrl={shopUrl} token={safeToken} showTrialNote={isTrial} />
    ) : (
      <StoreProduceDesk state={state} onChange={commit} shopUrl={shopUrl} token={safeToken} showTrialNote={isTrial} />
    )
  ) : chatlyUi ? (
    <ProduceChatlyStorefront ... /> // كما هو، بدون تغيير
  ) : ( ... )
  ```
  أي: بدّل الفرع الحالي `desk ? <StoreProduceDesk .../> : ...` بحيث يتحقق من `chatlyUi` أيضاً داخل فرع `desk`، تماماً كما هو محقَّق فعلاً داخل فرع المتجر (`chatlyUi ? <ProduceChatlyStorefront> : <StoreLiveActivityCartShop>`). هذا يعني أن `<StoreProduceDesk>` القديم **يبقى كما هو حرفياً، بدون أي تعديل فيه** — الملف الجديد بديل كامل موازٍ له، وليس تعديلاً عليه.
- بهذا يمكنك بعدها حذف كلاس `produce-chatly-desk` والتنسيقات المرتبطة به من `produceChatly.css` إن رغبت (لم تعد الحاجة إليها بما أن المكوّن الجديد سيحمل تنسيقه الخاص كما في مرجع Chatly)، أو تركها — قرارك، لا يؤثر على الوظيفة.

## 3) جدول الربط — كل عنصر في تصميم Chatly ↔ مصدره الحقيقي في الإنتاج

| عنصر في تصميم Chatly | المصدر الحقيقي الذي يجب استخدامه | ملاحظة |
|---|---|---|
| شريط "مساحة التشغيل / خضارنا1" + بطاقة "حالة البائع" أعلى القائمة الجانبية | `state.host.shopName`، و`state.host.acceptingOrders` بدل `receiving` الوهمي | لا حاجة لمتغير state جديد — استخدم الحقل الحقيقي مباشرة |
| عناصر التنقّل الست (نظرة عامة/الطلبات/المنتجات والمخزون/الموقع والساعات/الدفع المباشر/أدوات المشاركة) | `useState<Section>` محلي داخل المكوّن الجديد للتبديل بين الأقسام — هذا الجزء فقط (أيّ قسم ظاهر) يمكن أن يكون state محلي جديد، لأنه عرض فقط ولا يمسّ بيانات العمل | Badge عدد "الطلبات" = `fresh.length` الحقيقي (نفس الحساب الموجود حالياً بأعلى الملف القديم) |
| "دليل الاستخدام" في نهاية القائمة | `StoreDeskGuideLink` الحقيقي (`to={ROUTE_PATHS.STORE_PRODUCE_SUPPORT}`) | لا تستبدله بزر وهمي `notify(...)` |
| "أرشيف الطلبات" في نهاية القائمة | يفتح نفس بيانات `StoreDeskArchiveDock` الحقيقية — إمّا رابط لقسم فرعي، أو ينقل لتبويب الطلبات حيث يوجد الأرشيف الفعلي | لا تستبدله بـ`notify("تم فتح الأرشيف")` وهمي |
| "صفحة العميل" أسفل القائمة الجانبية | `shopUrl` الحقيقي (prop موجود بالفعل) بدل `href="/khudarana"` الثابت | |
| زر "التنبيهات" (جرس) في الهيدر | **هذا هو الأهم:** يوجد مكوّن حقيقي فعلي بهذا الغرض تماماً هو `StoreDeskOrderAlert` (شريط تنبيه صوتي حقيقي بخيارات نغمة/مستوى صوت عند وصول طلب جديد، عبر `useStoreDeskOrderAlert`). **لا يجوز استبداله بجرس زخرفي يعرض toast وهمي "لا توجد تنبيهات جديدة".** إمّا أن يُدمَج `StoreDeskOrderAlert` بصرياً كأيقونة/قائمة منسدلة في الهيدر بنفس شكل جرس Chatly، أو يبقى شريطاً في أعلى قسم "نظرة عامة" — المهم أنه نفس المكوّن الحقيقي بكامل وظيفته | راجع `StoreDeskOrderAlert.tsx` لخيارات التصميم قبل القرار |
| زر تبديل "يستقبل الطلبات / متوقف مؤقتاً" في الهيدر | نفس المنطق الحقيقي الموجود حالياً بأسفل الملف القديم: `onChange({ ...state, host: { ...state.host, acceptingOrders: !state.host.acceptingOrders } })` | انقله بصرياً فقط للهيدر |
| عنوان اللوحة "إدارة خضارنا1" | `StoreDeskControlTitle` الحقيقي (مع `trialNote` عند `showTrialNote`) — لا يُحذف، فقط يُعاد وضعه بصرياً داخل الهيدر الجديد | ملاحظة التجربة (`STORE_PRODUCT_TRIAL_PRODUCTS.produce.deskNoteAr`) يجب أن تبقى ظاهرة إن كانت مفعّلة |
| مقياس "طلبات جديدة" | `fresh.length` الحقيقي | |
| مقياس "حضور مباشر" (كان "7" وهمي) | **يجب أن يكون رقماً حقيقياً** من `StoreShopPresenceCount` / `useStoreShopPresence({ role: 'desk', productTag: 'store_produce_live', token })` — الرقم الحقيقي فعلياً موجود بالفعل يُعرض حالياً كنص "يتصفح المتجر الآن: N" داخل قسم الطلبات القديم. انقل نفس الرقم للبطاقة، **ولا تضع رقماً ثابتاً** | |
| مقياس "أصناف وصلت اليوم" | `state.shelf.filter(item => item.arrivedToday).length` الحقيقي | |
| مقياس "إجمالي اليوم" (كان "92" وهمي) | **لا يوجد حالياً حقل تجميع "إجمالي مبيعات اليوم" جاهز في `ProduceLabState`.** لا تخترع رقماً. إمّا: (أ) احسبه بنفسك بجمع `total` لكل الطلبات الحيّة + المؤرشفة التي تاريخها اليوم إن كان ذلك ممكناً بأمان من البيانات المتاحة، أو (ب) احذف هذه البطاقة من الشبكة (اجعلها 3 بطاقات بدل 4) بدل عرض رقم غير حقيقي. **قرارك بين الخيارين، لكن ممنوع رقم وهمي أو ثابت.** | نقطة قرار صريحة لك |
| قائمة "الطلبات الجديدة" المصغّرة (أول طلبين) في نظرة عامة | نفس بيانات `fresh`/`working` وأزرار `StoreDeskTicketActions` الحقيقية بالضبط كما في القسم القديم (استلام/إنهاء تستدعي `receiveOrder`/`finishOrder` الحقيقيتين) | |

| تبويب "الطلبات" بمسارين (جديدة/مستلَمة) | نفس `fresh`/`working` + `StoreDeskTicketActions` + رابط واتساب الحقيقي (`produceWhatsAppText`) + **زر الدردشة الحقيقي**: مرجع Chatly يفتح نافذة دردشة وهمية بردود جاهزة ("نورة متصلة الآن")، بينما الإنتاج لديه `StoreProduceDeskChat`/`StoreProduceBuyerChat` حقيقي (`state.chats`, `onChange`). **استبدل نافذة الدردشة الوهمية بالمكوّن الحقيقي دون أي رد تلقائي مزيّف** | |

| تبويب "المنتجات والمخزون" + زر "إدخال جماعي" | شبكة `state.shelf` الحقيقية مع أزرار `toggleStock`/`toggleArrived` الحقيقية، وزر "إدخال جماعي" يفتح/يعرض `StoreProduceIngest` الحقيقي (يحتوي بالفعل تحليل نص حر لقائمة أصناف — لا تبني نظام إدخال جماعي مواز) | |

| ركن الدعم/النمو أسفل يسار الشاشة | `StoreDeskCornerDock` مع `StoreDeskGuideLink` و`StoreDeskHelpSupport` الحقيقيين — يجب أن يبقيا ظاهرين في أي تصميم جديد، فلا تُخفهما لصالح الشكل الجديد | |

## 4) ممنوعات صريحة (بالإضافة لما سبق)

1. **لا تلمس `StoreProduceDesk.tsx` القديم إطلاقاً** — المكوّن الجديد `ProduceChatlyDesk.tsx` مستقل وموازٍ تماماً، تماماً كما فُعل مع `ProduceChatlyStorefront.tsx` مقابل `StoreLiveActivityCartShop`.
2. **لا تُغيَّر أي مكوّن مشترك** (`StoreShopPlaceDesk`, `StoreDirectPayDesk`, `StoreShopHoursDesk`, `StoreShopIdentityDesk`, `StoreShopBackgroundDesk`, `StoreDeskArchiveDock`, `StoreLiveShopShareDesk`, `StoreDeskCornerNav`, `StoreOpsSection`, إلخ) من الداخل — هذه تُستخدم أيضاً في لوحات تمويناتا1/طبختنا1/حلانا1/خضارنا1-القديم. أي تغيير داخلي فيها سينعكس على الجميع. إن احتجت تخصيصاً بصرياً إضافياً، أضِف prop اختياري جديد بقيمة افتراضية آمنة (`= false`/`= true` بلا أثر على الاستدعاءات الأخرى) — تماماً بنفس أسلوب `showDevNotice`/`showLiveMark` الذي استُخدم بنجاح في `StorePurchasedShell.tsx`، **ولا تُعدّل السلوك الافتراضي**.
3. **لا زر تبديل ثابت/متجول** (راجع البند الحرج أعلاه).
4. **لا بيانات وهمية أو أرقام ثابتة** في أي مقياس أو بطاقة.
5. **لا دردشة وهمية بردود جاهزة** — الدردشة الحقيقية فقط.
6. **لا تبسيط لنموذج الدفع المباشر.**
7. **هذا التغيير لا يمسّ توكن `produce-lab` فقط إطلاقاً غير هذا** — أي توكن حقيقي آخر لخضارنا1 (أي بائع فعلي مشترك) يستمر بعرض `StoreProduceDesk` القديم دون أي تغيير حتى قرار التعميم (مسار ج) لاحقاً، ولا تُفعِّل `VITE_STORE_PRODUCE_CHATLY_UI_ALL` بأي حال ضمن هذا التكليف.
8. لا تلمس لوحة العميل (`ProduceChatlyStorefront.tsx`) ولا صفحة العميل القديمة (`StoreLiveActivityCartShop`) — هذا التكليف للوحة التشغيل (desk) فقط.

## 5) بعد الانتهاء — قبل أن تقول "ادفع"

أرسل لي وصفاً مشابهاً لما أرسلته في مسار (ب): الملفات التي تغيّرت (يجب أن تكون فقط: ملف جديد `ProduceChatlyDesk.tsx`، تعديل بسيط على `StoreProduceShopPage.tsx` لإضافة الفرع، وربما حذف/تعديل طفيف على `produceChatly.css`)، وتأكيد صريح أن:
- `StoreProduceDesk.tsx` لم يتغيّر حرفاً واحداً.
- كل مقياس/بطاقة تعرض بيانات حقيقية لا وهمية.
- لا يوجد زر تبديل ثابت/متجول.
- الدفع المباشر والدردشة والأرشيف والإدخال الجماعي كلها المكوّنات الحقيقية بلا تبسيط.

بعدها سأسحب الكود بنفسي وأشغّل `tsc` وأراجع الديف قبل الموافقة على الدفع، كالمعتاد.
