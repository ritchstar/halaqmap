# تسليم شاتلي: نموذج حلاق ماب التجريبي (Pilot) — غلاف المنتج + لوحة اليوم + محطة التشغيل

**التاريخ:** 2026-09-11
**النطاق:** منتج واحد فقط — **حلاق ماب (A-01)** — كتجربة تطبيق أولى قبل التعميم على باقي المنتجات.
**القرار المعتمد:** التركيبة الأولى (الأكثر اتساقاً): غلاف ملف A-01 + لوحة اليوم + محطة التشغيل، مبنية كقالب واحد موحّد قابل لإعادة الاستخدام لاحقاً على منتجات أخرى لا تملك أداة تشغيل حالياً (كوافير ماب، لاونجا1، أفراحي1، أجواء1، كاردي8) — **وليس** على المنتجات التي لديها أدوات تشغيل (Desk) تعمل فعلياً حالياً (تمرتنا1، طبختنا1، خضارنا1، كافينا1، مطعمنا1).

## ⚠️ ملاحظة مهمة قبل البدء

1. **next/image مرة أخرى:** كما في الجولة السابقة (دعم صور المنتجات)، الأرجح أن شاتلي استخدم مكوّنات Next.js في بنائه الداخلي. تأكد من مراجعة أي `import Image from "next/image"` واستبداله بـ `<img>` عادي عند النقل لمشروعنا (Vite + React Router).
2. **رابط المعاينة العام لم يتحدث بعد:** أضاف شاتلي مساراً مباشراً `/halaq-map` داخل بيئة Imagine الخاصة به، لكن عند التحقق من `https://halaqmap-store-management.imaginesites.app/halaq-map` ظهرت صفحة 404 — أي أن التحديث لا يزال داخل معاينة Imagine الداخلية فقط ولم ينعكس بعد على رابط المشاركة العام (نفس النمط الذي حدث في الجولة الخاصة بالخلفية التفاعلية، حيث تأخر الظهور على الرابط العام بضع دقائق). يُنصح بإعادة التحقق من الرابط لاحقاً، أو الاعتماد مباشرة على المواصفات والكود أدناه دون انتظاره.
3. **الكود الكامل (JSX) للواجهات الثلاث لم يُسلَّم حرفياً هذه الجولة** — شاتلي أعطى بنية البيانات ومنطق الترابط بدقة (أدناه)، بالإضافة إلى المواصفات البصرية التفصيلية من الجولة السابقة (المقاسات، المواضع، ألوان الهوية). إذا احتاج كروسور الكود الحرفي الكامل (TSX) للصفحات الثلاث قبل البدء، يمكن أن أطلبه من شاتلي في جولة إضافية — أخبرني إن كنت تريد ذلك.

## 1) البنية العامة

نموذج واحد مشترك (وليس ثلاث صفحات منفصلة بالكامل) يضم ثلاث واجهات تتبادل نفس البيانات:

- **غلاف ملف A-01** — تعريفية، تشرح حلاق ماب للزائر
- **لوحة اليوم** — واجهة العميل النهائي (الحجوزات، الحلاقون المتاحون، وقت الانتظار)
- **محطة التشغيل** — لوحة صاحب الصالون (خمس حالات: وارد ← يحتاج مراجعة ← قيد التنفيذ ← جاهز ← مكتمل)

الثلاثة تظهر من نفس الصفحة الرئيسية للمنتج ومن مسار مباشر `/halaq-map` (حسب تسمية شاتلي الداخلية — يُعاد تسميته حسب تسمية مسارات مشروعنا الفعلية، مثلاً ضمن `ROUTE_PATHS` الحالية).

## 2) شكل بيانات الحجز (Booking)

الحقول التي يتضمنها كل حجز تجريبي:
- رقم الحجز (id)
- اسم العميل
- نوع الخدمة (قص شعر / لحية / قص + لحية)
- الحلاق
- الموعد
- وقت الانتظار التقريبي
- الحالة الحالية (OrderStatus)
- ملاحظة اختيارية

## 3) مشاركة البيانات بين الصفحات الثلاث

حالة React واحدة فقط على مستوى النموذج المشترك — لا نسخ منفصلة لكل صفحة:

```tsx
const [bookings, setBookings] = useState<Booking[]>(initialBookings);
```

الغلاف، لوحة اليوم، ومحطة التشغيل الثلاثة تستقبل نفس `bookings` (كخاصية/prop أو عبر context مشترك). أي تعديل من محطة التشغيل ينعكس فوراً في لوحة اليوم لأنها تقرأ من نفس المصدر — لا حاجة لأي مزامنة يدوية أو نداء شبكة بين الصفحتين في هذه المرحلة التجريبية.

## 4) منطق الانتقال بين الحالات

```ts
const nextStatus: Partial<Record<OrderStatus, OrderStatus>> = {
  incoming: "review",
  review: "active",
  active: "ready",
  ready: "complete",
};
```

```tsx
const advanceBooking = (id: string) => {
  setBookings((current) =>
    current.map((booking) =>
      booking.id === id && nextStatus[booking.status]
        ? { ...booking, status: nextStatus[booking.status] as OrderStatus }
        : booking,
    ),
  );
};
```

**ماذا يحدث بالضبط عند ضغط صاحب الصالون على "الحالة التالية" في محطة التشغيل:**
1. يُعثر على الحجز عبر `id`
2. تُقرأ حالته الحالية (`status`)
3. تُستخرج الحالة التالية من خريطة `nextStatus`
4. تُبنى نسخة جديدة من قائمة الحجوزات (immutable update — لا تعديل مباشر على المصفوفة الأصلية)
5. يُعاد رسم لوحة اليوم تلقائياً بسبب تغيّر الحالة المشتركة (React state) — بدون أي كود إضافي للمزامنة
6. يتغيّر عمود الحجز في محطة التشغيل نفسها فوراً أيضاً

## 5) ما يمكن لكروسور فعله عند الدمج الفعلي

- استخدام نفس المكوّن المشترك (البنية الثلاثية) في الصفحة الرئيسية للمنتج والمسار المباشر لحلاق ماب
- استبدال `initialBookings` التجريبية ببيانات حجوزات حقيقية (من قاعدة البيانات الفعلية) عند الربط الحقيقي لاحقاً
- الإبقاء على نوعي `Booking` و`OrderStatus` كما هما قدر الإمكان حتى لا تتغيّر واجهات الصفحات الثلاث
- استبدال `advanceBooking` بطبقة حفظ حقيقية (نداء API فعلي) عند ربط الحجوزات الحقيقية — حالياً البيانات تجريبية بالكامل ولا تُرسل إشعارات أو بريداً فعلياً

## 6) المواصفات البصرية (من الجولة السابقة — لا تزال سارية لهذا النموذج)

**استخدام الشعار (logoSrc) في الصفحات الثلاث:**

| الصفحة | المقاس (سطح مكتب) | المقاس (جوال) | الموضع |
|---|---|---|---|
| غلاف ملف A-01 | 112–144px | 80–96px | أعلى يمين بطاقة الغلاف، داخل إطار "ملصق تعريف صناعي" |
| لوحة اليوم | 64–88px (حتى 96px للهوية القوية) | — | رأس اللوحة بجانب اسم النشاط |
| محطة التشغيل | 40–56px (72px في حالة الفراغ) | — | رأس المحطة بجانب اسم المنتج — لا يتكرر داخل كل بطاقة طلب |

**الهوية البصرية لهذا النموذج تحديداً ("ملف حلاق مختوم"):** ورق فهرسة فاتح، حبر أزرق (نفس `#1d4f69` من هوية الكتالوج)، ختم طوبي (`#b84c3a`)، حدود دقيقة، حواف شبه مربعة — امتداد مباشر لنفس هوية "خريطة الحل" الأصلية، وليست هوية منفصلة.

**الجوال:** محطة التشغيل تتحول من خمسة أعمدة متجاورة إلى بطاقات/ألسنة تبويب أفقية قابلة للتمرير؛ لوحة اليوم تبقى مقروءة رأسياً دون ازدحام.

**مثال محتوى لوحة اليوم لحلاق ماب تحديداً:** الحلاقون المتاحون حالياً، أقرب موعد شاغر لكل حلاق، خدمات سريعة (قص شعر / لحية / قص + لحية)، وقت الانتظار التقريبي، زر "احجز دورك"، وتنبيه مثل "عدد العملاء قبلك: 2".

**مثال انتقال حالات محطة التشغيل لحلاق ماب:** وارد = العميل أرسل طلب حجز ← يحتاج مراجعة = الموظف يختار الحلاق والوقت ← قيد التنفيذ = العميل دخل الدور/بدأت الخدمة ← جاهز = انتهت الخدمة وجاهز للدفع/الاستلام ← مكتمل = انتهت الزيارة.

## الخلاصة

هذا تسليم كافٍ لبدء التنفيذ الفعلي لحلاق ماب فقط: بنية البيانات، منطق الترابط الحي بين لوحة اليوم ومحطة التشغيل، والمواصفات البصرية الدقيقة. الكود الحرفي الكامل (JSX) للثلاث واجهات لم يُطلب بعد حرفياً — إذا كان كروسور يفضل كوداً جاهزاً للصق المباشر بدل البناء من المواصفات، أخبرني لأطلبه من شاتلي في جولة تالية.
